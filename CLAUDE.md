Documentation site for CoMapeo (Mobile + Desktop), built with Docusaurus v3. Content is authored in Notion and exported to Markdown by a small pipeline in this repo.

This file is short by design — it's a routing document. For depth, follow the links.

## Toolchain

- **Runtime:** Node 24+ with native TypeScript execution (no transform step). Run `.ts` files directly via `node script.ts`.
- **Package manager:** pnpm. The lockfile is `pnpm-lock.yaml`. Do NOT introduce `npm`, `yarn`, or `bun`.
- **Test runner:** Vitest.
- **Build:** Docusaurus.

Common commands:

```bash
pnpm install          # install deps
pnpm dev              # start Docusaurus dev server
pnpm build            # build static site
pnpm serve            # serve built site
pnpm test             # run vitest
pnpm typecheck        # tsc --noEmit
pnpm lint             # eslint src
```

## The `legacy/` rule

Everything in `legacy/` is from the previous architecture (Bun runtime, database-driven Notion sync, two-branch with `content-lock.sha`). **There is no production site relying on it.** Do not:

- Import from `legacy/`
- Mirror its file/folder structure when designing new code
- Apply its style or conventions to new code
- Use it to answer "how should this work" — use the plan docs instead

The plan docs in `.claude/skills/notion-markdown-export/` supersede whatever the old `AGENTS.md` and `CLAUDE.md` (now at `legacy/AGENTS.legacy.md` and `legacy/CLAUDE.legacy.md`) used to say.

## Coding style

- TypeScript everywhere. No build step — Node 24 strips types natively.
- ESM (`"type": "module"` in package.json).
- Prettier defaults: 2 spaces, semicolons, double quotes. Don't fight the formatter.
- Small, focused files. Flat folder structures unless size genuinely demands hierarchy.
- Trust internal code; validate only at system boundaries (Notion API responses, env vars).
- Default to writing NO comments. Only add one when the *why* is non-obvious — hidden constraint, workaround for a bug, surprising upstream behavior.

## What's where, mentally

Two distinct components with different lifecycles:

1. **Notion export pipeline** (`scripts/notion-export/`) — fetches from Notion, writes `.md` + `_category_.json` + `_redirects` into the repo. Runs offline on CI schedule or `workflow_dispatch`.
2. **Docusaurus build configuration** (`docusaurus.config.ts` + `src/`) — config, plugins, theme. Runs during `docusaurus build`.

Don't mix them. Don't fetch from Notion at build time. Don't let Docusaurus plugins import from `scripts/notion-export/`.

## Where to add things

This section grows as Sprints A–E land.

- New Docusaurus plugin → `src/plugins/<plugin-name>/`
- New theme swizzle → `src/theme/...` (Docusaurus convention)
- New build-time tooling → `scripts/<tool-name>/` (flat structure preferred)
- New content (English) → authored in Notion at the page tree root, exported by the pipeline
- New translation → Weblate (Phase 4.5)

## scripts/notion-export/ (Sprint A onwards)

Offline pipeline that fetches the Notion page tree, transforms output, writes to `docs/`. See `scripts/notion-export/README.md` for the file-by-file map. Flat structure — no `lib/` subfolder.

Smoke-test commands:

```bash
pnpm notion:walk                                         # uses NOTION_ROOT_PAGE_ID from .env
pnpm notion:walk 360c90f22b6381b5a108c49dfb1ff9af        # explicit root
pnpm notion:walk 360c90f22b6381b5a108c49dfb1ff9af --verbose
pnpm notion:export                                       # stub until Sprint B
pnpm test scripts/notion-export                          # run module tests
```

Adding a new transform:

1. Add the function to `scripts/notion-export/transform.ts` (or a new file if it's substantial)
2. Pure function: `(markdown: string) => { markdown: string; report?: T }`
3. Write tests in `transform.test.ts` (no env dependency — see `parse.ts` / `transform.ts` for the pattern)
4. Wire into the orchestrator's per-page transform sequence (currently in `scripts/notion-export/index.ts` — Sprint B fills this in)

Adding a fetch call:

1. Add a typed wrapper to `scripts/notion-export/fetch.ts`
2. It must go through the `notionFetch` pipeline (rate-limited, retried, http-error-aware) — don't reach for `fetch()` directly
3. Validate any path-component page IDs via `normalizePageId(id)` first
